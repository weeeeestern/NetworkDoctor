# 시연 흐름 보강 설계: 장애 → Slack 알림 → Grafana → 인시던트 레포트

> 상태 (2026-11-12): Slack 연동(3.1)과 Grafana·UI 링크는 PR #27(`notify`, `links`)로, 나머지는 이 문서 기준 PR로 구현했다. 랩은 상관 그룹을 끈다(`correlationWindow: 0s`). 시연 장애 시나리오는 아직 정하지 않았다.

## 1. 왜

시연 영상에서 "장애가 나면 NetworkDoctor가 알려주고, 원인까지 짚어준다"를 보여줘야 한다.
지금은 두 군데가 비어 있다.

- **알림이 없다.** Alertmanager는 백엔드 webhook으로만 보낸다. Slack·Discord 연동이 없다.
- **레포트가 안 읽힌다.** 인시던트 UI 상세가 영어 텍스트 나열이라, 몇 초 안에 결론이 보이지 않는다.
  목록도 `network-congestion` / `inc-3fa9…` 같은 이름이라 클릭해야 무슨 일인지 안다.

Grafana 룰 대시보드(Trigger / Supporting / Exclusion, 발화 구간 표시)는 이미 시연에 충분하다.

## 2. 시연 흐름

| # | 장면 | 화면 | 보는 사람이 얻는 것 |
| --- | --- | --- | --- |
| 0 | 시나리오 소개 | 설명 자막 + Grafana 오버뷰 (정상 상태) | 무엇을 어떻게 망가뜨릴지, 평소엔 어떤 모습인지 |
| 1 | 장애 주입 | 터미널 (`scripts/repro/*`) | catshop에 장애를 낸다 |
| 2 | 알림 도착 | Slack `#incidents` | 어디서 무슨 일이 났는지 |
| 3 | 이상 흐름 확인 | Grafana 룰 대시보드 (알림 속 링크) | 그래프로 "뭔가 이상하다" |
| 4 | 분석 완료 | 같은 Slack 메시지의 스레드 댓글 | 원인 한 줄 + 레포트 링크 |
| 5 | 레포트 확인 | 인시던트 UI 상세 (위→아래 스크롤) | **증상과 추정 원인**, 근거, 배제한 원인, 조치 |

### 시연 장애: Rule 1 네트워크 혼잡 (`rule1-congestion.sh`)

장면 0에서 아래 세 줄을 자막으로 설명하고 시작한다.

- **무엇을:** catshop을 호출하는 클라이언트 파드의 송신 패킷 30%를 버린다(`tc netem`).
- **결과:** 사용자 입장에서는 "쇼핑몰이 느려졌다"만 보인다. 원인이 네트워크인지 앱인지 DNS인지는 겉으로 알 수 없다.
- **기대:** NetworkDoctor가 TCP 재전송 급증을 잡아내고, DNS·conntrack·NetworkPolicy가 아니라 해당 노드의 네트워크 문제라고 짚어낸다.

고른 이유:

- 증상(느려짐)이 직관적이다.
- 배제한 원인 목록이 풍부하다.
- 지금까지 예시로 써 온 시나리오라 화면 문구와 그대로 이어진다.

촬영할 때 주의할 점:

- 주입 후 약 4분 뒤에 알림이 발화하고, 분석 완료까지는 최대 18분 걸린다. 대기 구간은 편집으로 자른다.
- 같은 스크립트를 다시 돌리려면 이전 알림이 resolved 되고 15분이 지나야 한다. 재촬영 일정을 그만큼 잡는다.

원칙:

- **역할 분리.** Slack은 알려주고, Grafana는 그래프를 보여주고, UI는 결론을 설명한다.
  UI에 그래프를 다시 그리지 않는다. UI에서 긴급함을 연출하지 않는다.
- **알림은 인시던트당 한 번만 울린다.** 후속 소식은 스레드로 붙인다.
- **화면에 나오는 모든 글은 자연스러운 한국어로 쓴다.**

## 3. 무엇을 만드나

### 3.1 Slack 알림 (백엔드)

- **방식.** Slack 앱 봇 토큰(`chat:write`)으로 `chat.postMessage`를 쓴다.
  일반 웹훅은 스레드 댓글을 달 수 없어서 쓰지 않는다.
- **1차 (알림 수신 즉시).** 그룹 대표 인시던트만 채널에 메시지를 올린다.
  - 내용: 시나리오 한국어 이름, 증상, 노드·서비스, 발생 시각
  - 링크: Grafana 룰 대시보드, 인시던트 UI 상세
- **스레드 댓글.** 응답의 `ts`를 인시던트에 저장하고, 이후 소식은 그 스레드에 단다.
  - 분석 완료: 추정 원인 한 줄, 신뢰도, "레포트 보기" 링크
  - 분석 실패: 실패했다는 사실과 UI 링크
  - 함께 묶인 알림: 그룹 멤버가 생기면 "함께 묶인 알림: …" 한 줄
  - 복구: 🟢 복구됨 — 대표 인시던트가 resolved 될 때 한 번 (멤버 복구는 따로 안 알림)
  - 재분석: 재분석 결과도 같은 스레드에 새 댓글로 단다
- **대상.** `smoke-*` 룰은 Slack에 올리지 않는다.
- **그룹 판단.** 그룹은 알림 수신 시점(`store.go`)에 이미 정해지므로, 대표인지 여부를 바로 알 수 있다.
- **설정이 없으면 끈다.** 토큰이나 채널이 없으면 Slack 기능 전체를 끈다.

### 3.2 링크 주소 (Helm 설정)

- `grafana.url`, `ui.url`을 values로 받는다. 랩 값은 각각의 NodePort 주소다.
- Grafana 링크 형식: `<grafana.url>/d/nd-rule-<N>?from=<발생-10분>&to=<복구+10분 또는 now>&var-node=<노드>`
  대시보드 uid는 차트가 고정 배포하므로 어느 클러스터에서나 같다.
- **비어 있으면 해당 링크를 숨긴다.** UI와 Slack 모두 같은 규칙을 따른다.
- Slack 토큰은 Secret으로 받는다. 채널은 values로 받는다.

### 3.3 Holmes 출력 (스킬 8개 공통)

- 출력 스키마에 짧은 요약 필드를 추가한다.
  ```yaml
  summary:
    symptom: "catshop 응답 지연 1.8s (평소 120ms)"
    cause:   "worker1 NIC 혼잡으로 TCP 재전송 급증"
  ```
  "평소 값"은 Holmes가 이미 하는 직전 구간·피어 비교에서 가져온다.
- **한국어 작성 지침**은 백엔드가 Holmes에 보내는 질문(`holmes.BuildAskWithFacts`)에 한 번만 넣는다. 10줄 안팎으로 짧게 쓴다.
  스킬 8개에 복사하지 않아 한 곳에서 고칠 수 있고, Holmes를 재시작하지 않아도 반영된다. `SKILL.md`에는 `summary` 스키마만 추가한다.
  - 문장: 번역투·상투어 금지. NomaDamas/k-skill `korean-humanizer`의 핵심 규칙에서 추린다(라이선스 확인 후).
  - 용어: [쿠버네티스 한글화 모범 사례](https://kubernetes.io/ko/docs/contribute/localization_ko_best_practice/)를 따른다(파드, 노드, 서비스 등).
  - 그대로 두는 것: 지표명, 리소스명, 라벨 값, 필드 키(`rule_id`, `confirmed` 등 enum 포함)
- **결론별 표시.** 두 번째 줄의 라벨과 문장은 `investigation_status`에 따라 바뀐다. UI, Slack, 레포트가 모두 같은 규칙을 따른다.
  - `confirmed`: 라벨 **추정 원인**, `summary.cause`에는 원인을 쓴다.
  - `excluded`: 라벨 **이 시나리오 아님**, `summary.cause`에는 배제한 이유와, 보이면 더 그럴듯한 원인을 쓴다.
  - `inconclusive`: 라벨 **원인 불확실**, `summary.cause`에는 무엇이 모자라서 판단을 못 했는지 쓴다.
- `summary`가 없는 옛 결과는 `symptom_summary`(알림 annotation)와 `root_cause`로 대신 보여준다.

### 3.4 인시던트 UI: 상세 화면 (위→아래)

1. **요약 카드**
   - **증상** / **추정 원인** 두 줄을 크게 보여준다.
   - 칩은 `신뢰도 높음|보통|낮음`과 발생 시각 두 개만 둔다.
   - 오른쪽에 "Grafana에서 자세히 보기 →" 링크를 둔다.
2. **① 원인 분석**: `root_cause` 문단
3. **② 근거**
   - "알림을 일으킨 신호"(trigger)는 빨간 세로줄로 표시한다.
   - "함께 움직인 신호"(supporting)는 노란 세로줄로 표시한다.
   - 각 줄 아래에 출처 지표명을 작게 적는다.
4. **③ 배제한 원인**: 취소선 친 원인 이름 옆에 배제한 이유를 적는다.
5. **④ 권장 조치**: 번호 목록으로 보여준다. 아래에 "추가로 확인하면 좋은 것"을 붙인다.
6. **▸ 상세 정보 (기본 접힘)**: 메타(클러스터·서비스·복구 상태·상관 그룹), 수집 원본 지표와 PromQL, 알림 라벨, 분석 비용(모델·토큰·비용)
- 버튼은 PDF 다운로드, 재분석 두 개를 유지한다. Markdown 링크는 접힌 영역으로 옮긴다.

### 3.5 인시던트 UI: 목록 화면

- **위쪽**
  - 왼쪽에 숫자 칩 2개(진행 중, 원인 분석 완료)를 둔다.
  - 오른쪽에 **최근 7일 막대그래프**(진행 중 / 복구됨)를 둔다.
  - 심각도 도넛, 분석 비율, 노드 순위는 뺀다.
- **표**는 상태 · 증상 → 추정 원인 · 노드 · 발생 순서로 열을 둔다.
  - 행 하나에 증상(굵게), 추정 원인(파란 글씨), 시나리오 한국어 이름과 신뢰도 칩을 담는다.
  - 분석 중이면 추정 원인 자리에 "원인 분석 중…"을 보여준다.
  - 그룹 멤버는 대표 행 아래 "함께 묶인 알림 N건"으로 접는다.
  - 심각도 열과 토큰·비용은 뺀다.
- **필터 탭**: 전체 / 진행 중 / 복구됨

### 3.6 한국어 전환 범위

- UI 문구 전부, Slack 메시지, 마크다운·PDF 레포트(`report/markdown.go`), Holmes 출력을 한국어로 바꾼다.
- 룰 이름 매핑(rule_id → 한국어 시나리오 이름)은 UI·Slack·레포트가 한 곳의 정의를 같이 쓴다.
  구현에서는 `internal/backend/incident/names.go`에 두고, API가 `scenario_name`·`headline`으로 내려준다.
- 시나리오 이름과 Grafana 대시보드는 **알림의 `rule_id`**(발화한 룰)를 따른다.
  Holmes가 다른 시나리오로 판단하면 그 내용은 추정 원인 문장에 드러난다.
- `rules/networkdoctor-scenario-rules.yaml`의 `summary`/`description` annotation도 한국어로 바꾼다.
  분석 전 Slack 1차 메시지와 목록 행의 증상이 이 문구라서다. 표시용 문구라 탐지 로직에는 영향이 없다.

## 4. 하지 않는 것

- UI 안에 지표 그래프 그리기 (Grafana 몫)
- Discord 지원 (Slack만)
- 실시간 자동 갱신, 경보 연출
- Alertmanager의 Slack 수신자 설정 (백엔드가 보낸다)

## 5. 주의할 점

- **eval 채점.** `eval/expectations.json`은 `root_cause`의 영어 키워드(`retransmi`, `loss`, `limit` 등)로 채점한다.
  한국어 출력으로 바꾸면 한국어 동의어를 추가해야 점수가 유지된다.
- **프롬프트 길이.** 한국어 지침이 길어지면 토큰 비용과 분석 품질에 영향이 있다.
  바꾸기 전과 후에 eval을 돌려 비교한다.
- **Slack 실패 처리.** Slack 호출이 실패해도 인시던트 처리와 Holmes 조사는 막지 않는다. 로그만 남긴다.

## 6. 시연 준비물

- Slack 워크스페이스 + `#incidents` 채널 + 봇 앱(`chat:write`)을 만들고, 봇을 채널에 초대한다.
- 봇 토큰을 k8s Secret으로 넣고, `grafana.url`·`ui.url`을 랩 NodePort로 설정한다.
- 시연 전에 장애를 몇 번 일으켜 7일 그래프와 목록에 이력을 쌓는다.

## 7. 구현자에게 맡기는 것

- Slack 메시지의 Block Kit 세부 레이아웃
- 인시던트에 추가할 필드 이름 (Slack `ts`·채널 등)
- CSS 세부와 한국어 시나리오 이름의 정확한 표현
